gRedraw

Definition: include theGUI.e

gRedraw(gdx id)
Description: Update the size and layout of all controls in the same dialog, and then, obviously, redraw them.

id: Identifier of the interface element. No gain/loss to be had by specifying gGetDialog(id).
pwa/p2js: Supported.
Notes: Invoking mid-paint, aka from within a REDRAW handler, is decidedly dodgy since the redraw currently underway is likely to announce "all done" (eg ValidateRect) before the latest request has actually had a chance to take proper(/on-screen) effect, even if it did successfully update all (internal) bits 'n bobs needed. Plus of course if you're not very careful risking an infinite loop of redraw->redraw->redraw->...

Generally speaking, I would say >99% of reasons to redraw are from mouse/keyboard/callback/timer events.

However things such as OpenGL and libmpv cannot be initialised until the relevant window has reached the drawing stage. Hence when theGUI detects that kind of call, it automatically schedules another redraw 1/8ths (125ms) later. You do need to make sure you only make such calls either in a one-off fashion or when something has genuinely changed, otherwise it will enter a busy loop, quite possibly becoming sluggish or even unresponsive, and waste CPU cycles and battery life for no good reason.
See Also: gShow
Technicalia gSetAttribute() should ideally trigger a redraw when needed, gimme a shout for any I've missed.

There were five similar routines in pGUI, namely IupRedraw(), IupRefresh(), IupRefreshChildren(), IupUpdate(), and IupUpdateChildren(), and I always ended up experimenting until finding the one ([and only] particular combination that) did precisely what I wanted.
The switch to fully emulated controls has (apparently) made any such distinctions completely unnecessary.

There's actually a second bNow parameter which (was always intended to be for internal use and) gives GTK an extra nudge, but it no longer seems to need it, so it'll probably get removed.
