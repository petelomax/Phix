gCalendar

Definition: include theGUI.e

gdx id = gCalendar([object ymd=NULL,] [rtn value_changed=NULL,] string attributes="", dword_seq args={})
Description: As used on the internal drop-down of a gDatePick(), but also available for permanent display.
Note this is a fixed-size/as-is control and unlikely to work properly with different sizes/fonts [TO-DO].
This is a paranormalised function. (see technicalia)
pwa/p2js: Supported.
Example: 
-- demo\theGUI\gCalendar.exw
include theGUI.e

gdx calendar = gCalendar(),
    hbox = gHbox({calendar}),`SPACE=AROUND`)
    dlg = gDialog(hbox,`gCalendar`)
gMainLoop(dlg)
Notes: Clicking on the central header "scrolls up" to months, years, decades, and centuries (see technicalia), unless the specified RANGE is already fully on-screen - should, for instance, you have to book a visit within the next ten days, half the time you won't be able to even get off the initial single-month view, or scroll left/right, unless that ten-day window happens to straddle a month end.

Anything outside the specified RANGE should appear greyed-out, have no hover effects, and be non-clickable.

You can also use the mousewheel instead of the left/right buttons, when enabled, and of course if the mousewheel doesn't do anything (=== left/right arrows greyed out), neither will clicking on the header.
Attributes:
RANGE Specify the permitted date range, default {{1800,1,1},{9999,12,31}} (see technicalia). If the start/end are integer they are treated as day offsets to the current date, so for example {-180,0} is the past 180 days (~6 months).

A perhaps too-subtle point is the range determines what is hoverable, and that in turn determines what is clickable. You shouldn't see any hover effects or be able to click on anything (wholly) outside the specified range, and of course any mouse navigation limits apply exactly the same to keyboard navigation (specifically left/right and [page] up/down).
VALUE The current date, timedate-compatible, eg {2025,12,31,0,0,0}, but does not quibble when set with a length-3 sequence, and returns a length-6 sequence with hms of 0s so that, (eg) format_timedate() doesn't either. Should you have a string such as "31/12/2025" you are expected to parse_date_string() it yourself.
Handlers: (optional) Specified at creation time or set using gSetHandler(calendar,"VALUE_CHANGED",value_changed).
VALUE_CHANGED Called after the value was interactively changed by the user.

procedure value_changed([gdx id,] timedate dt)
id: (optional) identifier of the element that activated the event.
dt: same as gGetAttribute(id,`VALUE`), which can o/c be used on-demand instead of a handler.
Technicalia As this is a paranormalised function, and with no expectation that you should memorise this lot, except maybe "draa", you can assume that all of the following are potentially perfectly valid, with the fairly obvious restrictions that any parameters must be in strict draa-order, and no args without attributes: 

                        gCalendar()
                        gCalendar(attributes)
                        gCalendar(attributes,args)
                        gCalendar(rid)
                        gCalendar(rid,attributes)
                        gCalendar(rid,attributes,args)
                        gCalendar(ymd)
                        gCalendar(ymd,attributes)
                        gCalendar(ymd,attributes,args)
                        gCalendar(ymd,rid)
                        gCalendar(ymd,rid,attributes)
                        gCalendar(ymd,rid,attributes,args)  -- (the full set)

Note that in practice ymd and rid are actually defined as object, and attributes as a sequence rather than a string, but verified to be of the documented types, after being repositioned via theGUI/paranormalise_draa().

Technically a gCalendar does not formally support dates prior to 1752, the introduction of the Gregorian calendar, however that limitation is not particularly strictly applied. Adoption of the Gregorian calendar varies by country, from 1582 to 2016, and I've done nothing about that. The following notes really date from prior to/during the implementation of the RANGE attribute and are more concerned with pedantically documenting some current and somewhat obscure behaviour than imposing any "hard" restrictions. Dates prior to 0 CE (aka 0 AD) broke some internal maths, and were therefore prohibited, plus all the '-' were not exactly pretty anyway. All months prior to 1752 are generally and somewhat flakily deemed to have 31 days, also format_timedate() produces "Anyday" when asked for a weekday of 31/12/1751 and earlier, and since Anyday is 8, (usually) show up as 25..31 with the 1st always on a "Monday", which kinda messes up the neater scrolling of >= 1752. In particular, the last few days of the previous month may be inconsistently displayed, and clicking on them lead to inconsistent results (pre-1752).

The bottom line is the start of RANGE can be as far back as 0/1/1, but not without some glitches, which given the limited practicality of such dates are left as an exercise for someone else to solve, as are -ve years, and that in Great Britain and its colonies, in 1752 the 2nd September was immediately followed by the 14th September.

Apparently there is also some small confusion over an "extra missing day" in 1800, due to it being a leap year in the Julian calendar but not in the Gregorian calendar, which I don't quite fully grasp (as in “why not 1900 too, then?”), hence the slightly strange start year of 1800 for RANGE.

Be advised so that scrolling months can resurrect Jan 31st, the control may internally hold the 31st of February, and in fact (as above) deliberately/visibly does so for any year prior to 1752, likewise it may sometimes internally hold the 31st July even when the upper range limit is 15th July, but otherwise that should not display/leak, nor, again, does it throw a hissy fit should you specify such things. Even immediately after setting 31/2 (for any year >=1752) you can expect to get the 28/29th back (at least, that is, as long as nothing in your application or anything it or the datepick invokes decides to suddenly throw an error).

Also, be aware I have tried my level best to make navigation (esp keyboard) as natural as possible, but some RANGE settings can introduce little niggles almost impossible to fully document, and quite probably a frankly frightening number of those could be classified as outright bugs, aka should you bash your head against a brick wall/range limit, don't expect zero dents.

UPDATE: I thought I'd got it working really well, until I went back and tried it with today's date but a range in last Novemember, and it didn't like that at all. Not only does it need to deal with bad setup better, but it exposed a few bugs, with the niggles just mentioned getting much more serious once the arrow keys stop doing anything. Needs a bit more work.

The following are images of the native controls, which gCalendar/gDatePick replicate as best they can.


At the top is a Windows SysDateTimePick32 control with the calendar drop-down in four title-click-states (½|¾).
In fact, since it was trivial, I added a fifth for a thousand years, much like the fourth's century but 17% more 0s, plus the temptation to merge similar 3-way is stronger than 2-way, so the code base actually shrank.
Below it is a GtkCalendar, there being no such thing as a GtkDatePick, and which doesn't do any of that state-stuff.
I couldn't convince myself a today button was all that useful, so left that out, otherwise theGUI mimics Windows.

There has been no attempt to implement any smooth transitions, that is left as an exercise for the reader. It would probably involve three gImages: old, new, and mix, on which to paint the fade/slide/zoom effects, plus a timer.

The dropdown itself is just a headerless gCanvas window, to the below/right unless that would go off-screen, with appropriate KEY/CLICK/MOUSEWHEEL handing.

Before the switch to emulated controls, this needed manual re-implementation anyway, since HTML has a perfectly decent drop-down but no always-visible equivalent I can find, and GTK the opposite [whereas WinAPI has both].

Ideally I suppose prior month enabled, prior month disabled, and this month disabled should be displayed in three different shades of grey, but that would be so easily-missable it is not worth bothering, whereas the presence/lack of hover-effects is/should be obvious.

One of the trickiest parts to implement was in fact preventing the user from navigating wildly off-range, so by all means be suspicious, but please think carefully (re click-ability-ness) before you open your gob.
