LiteZip

A wrapper for LiteZip, a free and easy-to-use zip file handler, as originally published on codeproject (RIP my dear friend), all the needed bits and pieces are now shipped with Phix in builtins\LiteZip, along with prebuilt dlls (Linux users are expected to build .so from source) and LiteZip.e one level up.

Allows the creation of and extraction from standard zip archives. Intended solely for use on (undamaged) self-created or previously carefully tested files, and in no way a rival to or replacement for the likes of 7-Zip and friends. Does not support symlinks or any form of encryption or passwords, just store and deflate, which is ~90% of all zip files.

One use of this, of particular importance for me, is software distribution, including Phix iteslf.

Requires LiteUnZip.32|64.dll (~34K each) and/or LiteZip.32|64.dll (~30K each) to be installed/distributed with any application that needs them, typically 32 or 64 not both, either in the application directory or builtins\ when it exists, but either may be absent, as long as only the appropriate subset of these routines are actually invoked.

None of these routines are supported by pwa/p2js.

Example 1:

Copy 
include builtins\LiteZip.e

atom hzip = UnzipOpenFile("phix.0.7.7.1.zip")

ZIPENTRY ze = new_ZIPENTRY()
integer numitems = UnzipGetItems(hzip,ze)
?{"numitems",numitems}  -- prints {"numitems",1156}

UnzipSetBaseDir(hzip,current_dir()&`\test`)

?UnzipFindItem(hzip,ze,"readme.txt")    -- prints 0 (ZR_OK)
?UnzipGetFileName(ze) -- prints current_dir()&`\test\readme.txt`

for i=1 to numitems do
    integer res = UnzipGetItem(hzip,ze,i)
    res = UnzipItemToFile(hzip,ze)
    printf(1,"\r%2d%%",{(i/numitems)*100})
end for

hzip = UnzipClose(hzip)
ze = free(ze)
puts(1,"\ndone\n")

Example 2:

Copy 
include builtins\LiteZip.e

atom hzip = ZipCreateFile("test.zip")
integer res
res = ZipAddFile(hzip,"LiteZip.dll")
res = ZipAddFile(hzip,"LiteUnzip.dll")
res = ZipAddDir(hzip,`test\LiteZip`,5)
res = ZipAddFolder(hzip,"empty")
hzip = ZipClose(hzip)
It does not get any simpler than that. You may prefer to declare res as an object, and test it for string after each step.

Not [yet] attempted (and I cannot see any need for them as yet):

ZipAddBuffer

ZipAddHandle[Raw]
ZipAddPipe[Raw]
ZipCreateHandle
ZipResetMemory
ZipOptions (options are TZIP_OPTION_GZIP and TZIP_OPTION_ABORT only anyway)

None of those are particularly important for dealing with real files and real .zip files, or eg ipc or embedded resources. Handles aren't really a good fit for Phix, I haven't tried anything with pipes but my gut instinct says LiteZip.e should know nothing about the innards of pipeio.e, and ZipResetMemory only applies to dynamically extending memory handles that we're not supporting because of the OS-specific cleanup they would need. I simply don't see any urgent or otherwise need to handle .gzip files, maybe (much) later. Which leaves full-zip-headers-in-memory buffers, the only use I can think of being downloading from a web page, but a LiteZip dll/so is not js-compatible anyway.

Further work: demo\junzip contains a skeleton pure-Phix program for analysing the zip headers and locating compressed blocks, but I put that on hold when I re-found the needed sources and managed to rebuild the Lite[Un]Zip dlls. I never quite got round to the final missing step of actually [un]compressing things but now I've got (eg) UnzipItemToBuffer() as well as some alternative in zlib1.dll (which knows didly squat about .zip file structure, being the reason I started work on junzip in the first place) that I was at one point planning to use. There's also an 800-line junzip\deflate.fasm which should be reasonably straightforward to transplant into a #ilASM{} statement, if it works that'd mean being able to unpack things without having to lug dll/so about, and lead to pure-Phix self extracting executables, which would be nice.
