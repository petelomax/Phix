gDropDown

Definition: include theGUI.e

gdx id = gDropDown(gdx list, [rtn value_changed=NULL,] string attributes="" dword_seq args={})
Description: Creates an interface element that is a simple text field with dropdown selector.

list: (mandatory) a gList to be used in the drop-down.
value_changed: (optional) procedure invoked when selection changes, see VALUE_CHANGED.
The handler and attributes on a gDropDown are the same as those on a gText, and distinct from a gList.

Returns the identifier of the created element.
pwa/p2js: Supported.
Example: 
-- demo\theGUI\gDropDown.exw
include theGUI.e

gdx list1 = gList({"one","two","three"}),
    drop1 = gDropDown(list1),
    list2 = gList(apply(true,ordinal,{tagset(21),true})),
    drop2 = gDropDown(list2,"VALUE=3"),
    hbox = gHbox({drop1,drop2},"MARGIN=13x13,GAP=15"),
    dlg = gDialog(hbox,"gDropDown",`SIZE=240x80`)
gMainLoop(dlg)

Notes: As per gDatePick except I am probably more likely to use and fix/enhance this sooner.
All the really important low-level tricky stuff (like alt-tab behaviour) works just fine, but there are two parts with [as yet] neither knowing the other even exists - however since (unlike gDatePick) there are no potential parsing/formatting issues, it is much more reasonable to expect theGUI to automate their collaboration, and (perhaps) implement some kind of smart filtering behaviour.

There is no "always down" version of a dropdown, and no plans to ever add one. Instead, if indeed that nonsense is in fact what you actually want, you are expected to plant a separate gText and gList (or whatever) on the dialog yourself, and make them interact in whatever weird way you think is right, yourself.
