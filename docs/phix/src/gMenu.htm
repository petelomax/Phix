gMenu

Definition: include theGUI.e

gdx menu = gMenu(sequence children, rtnn handler)
Description: Creates a menu with items, submenus and separators, which can be attached to a gDialog() or shown standalone.

children: a nested structure or internal version detailing the menu contents, sets DATA.
handler: routine for processing menu interactions, see HANDLER below.

Returns: the identifier of the created element.
pwa/p2js: Not yet supported, but pwa/js/poc/menus.html now seems pretty good/straightforward.
Example: 
-- demo\theGUI\gMenu.exw, somewhat simplified
include theGUI.e
constant MAIN_MENU = {{"&File",{{"&New\t",M_CTRL+'N'},
                                {"&Open\t",M_CTRL+'O'},
                                {"&Recent Files",{}},
                                {"&Close\t",M_CTRL+VK_F4},
                                "|",
                                {"E&xit\t",M_ALT+VK_F4}}},
                      {"&Edit",M_NOT_KEY+'E',
                               {{"Copy\t",M_CTRL+'C'}}},
                      {"&Help",VK_F1}}

function menu_handler(gdx menu, integer id)
    if c&&M_NOT_KEY==0 then
        {integer ch, bool ctrl,shift,alt} = gMenuCcsa(id)
--      key_handler(dlg,ch,ctrl,shift,alt) -- (offload it)
    end if
    return iff( id==M_ALT+VK_F4 ? TG_CLOSE : TG_DEFAULT )
end function

gdx menu = gMenu(MAIN_MENU,menu_handler),
    vbox = gVbox({menu/*,...*/}),
     dlg = gDialog(vbox,`gMenu`,`SIZE = 240x80`)
gMainLoop(dlg)

The above uses keystroke-like ids, M_CTRL+'N'..VK_F1, implying there is a KEY handler the menu handler can explicitly (as shown commented out to keep it runnable) offload work to (except M_NOT_KEY+x), but it doesn't hook that up for you magically.
The gMenuCcsa(integer id) function can be used to split such an id into the base character and bool flags expected by KEY, though it's actually your choice which handler it occurs in, key perhaps simplifying a gGetKeyName().
The menu-specific M_CTRL, M_SHIFT, M_ALT, and M_NOT_KEY (#20/10/08/0400_0000) are I trust pretty self-evident.
Equally it could use the somewhat less meaningful 1..7 menu-ids, or indeed almost any (unordered but > 0) integers.

The "children" structure (MAIN_MENU above) should be fairly self-explanatory. Each entry is:
  • {string menu_item, [gImage|"?[?]",] [bool [enabled,]checked,] integer id} for a "leaf" menu entry, or
  • any of {"|","-",'|','-'} for a separator (which are all treated identically), or
  • {string submenu, [gImage,] [[bool enabled,] integer id,] sequence children}
That final [nested sub-]children obviously follows the exact same rules, recursively, as deep as you like.
There is of course nothing to prevent such a menu from being built dynamically, rather than it being a constant.
[The "common sense" rules used to interpret shorthand notations, aka all those [], are fully detailed in the technicalia]

The MAIN_MENU above could (of course) equivalently be coded as: 

constant FILE_MENU = {{"&New\t",M_CTRL+'N'},
                      {"&Open\t",M_CTRL+'O'},
                      {"&Recent Files",{}},
                      {"&Close\t",M_CTRL+VK_F4},
                      "|",
                      {"E&xit\t",M_ALT+VK_F4}},
         EDIT_MENU = {{"Copy\t",M_CTRL+'C'}},
         MAIN_MENU = {{"&File",FILE_MENU},
                      {"&Edit",M_NOT_KEY+'E',EDIT_MENU},
                      {"&Help",VK_F1}}

Or specified (up-front) in the internal format, should that help.
Empty submenus (eg recent, and excluding top-level popups/drop-downs from a menubar) are automatically disabled.

There is no id on the "&File" menu, hence you cannot enable/disable it, and won't be notified on open or mouseover.
It would also not be possible to set/get the checked status, except for the fact that you cannot have checkboxes on submenus, only menu items, whereas it is an outright error not to have an id (or one <=0) on "leaf" items anyway.
In contrast, the presence of M_NOT_KEY+'E' on the "&Edit" menu means you get events and can change it.

When there is a tab character in the string, text to the left is left-aligned and the rest right-aligned, otherwise when it was at the end (as per "&New\t") or absent and id > M_ALT it constructs the key hint from the id instead. In general it doesn't make any sense to put that sort of keyboard shortcut on a submenu, and would overlap the '>'. As mentioned above (doesn't magically hook up) except for display it doesn't actually do anything at all with any(/most) mnemonics and shortcuts itself, instead you are expected to catch them(/any that don't work) in a KEY handler for the dialog. In the example given above, <Alt F>, <Alt E>, and <Alt H> should do what you expect automatically, but nothing else will.
Radios and
Checkboxes 		A menu item with "??" instead of an image starts a new one if needed and extends/becomes part of a radio set.
A menu radio group must be consecutive menu items; any non-radio, separator, or submenu terminates the group.
Unlike WinAPI/GTK there are no weird/confusing/conflicting restrictions on what ids you can use within a radio group.
A radio group with > 1 item checked triggers an error, see below for setting a default (first if none).
A menu item with the string "?" instead of an image generates a checked menu item.
Radios and checkboxes do not by default close the menu when clicked, unless the handler returns TG_CLOSE.
Popups: A menu can be the menubar of a dialog, as shown above, or a (right-click) popup menu.
For the former it would normally be the first element of a gDialog(gVbox({})) construct.
For a (top-level) popup it must not have a parent, ie be no part of any dialog hierarchy.

gPopupMenu(gdx menu, parent, integer x=TG_MOUSEPOS, y=TG_MOUSEPOS)
menu: a result from gMenu() which has not already been used as a barmenu for a dialog.
parent: (not optional) the (usually just clicked on) dialog to act as the (current/temp) parent for the menu.
x,y: (optional) screen position, literal values or TG_MOUSEPOS (but no other gShow-style flags).

A popup menu is displayed for the user and disappears when an item is selected, or on escape/outside clicks/focus loss.
Control returns immediately, with appropriate messages sent to the previously set handler.
Aside: Of course all submenus are technically popups, just ones that appear where their parent/menubar tells them to, and while you could in theory have a completely independent gMenu(EDIT_MENU), there is simply no way to specify the above initial example's gdx menu's embedded second-level version of that as the main parameter to gPopupMenu, or for that matter a gVbox's first element.
Attributes: All menu attributes are managed via the following rather than the usual gSet/GetAttribute().

gMenuSetAttribute(gdx menu, object id, string name, object v)
object v = gMenuGetAttribute(gdx menu, integer id, string name)
gMenuToggleInt(gdx menu, object id, string name)

menu,id 
both must always be provided, and id be non-zero.
Flat sequence[s] of them can be passed to set/toggle,
but not get (and are applied n*m rather than pair-wise).
name,v: as detailed below
ACTIVE Equivalent to the standard attribute (linked left), except for needing both a gdx and (non-zero) command-id.
(In fact the standard attribute applies to a menubar, but is meaningless on any popup, unless the application itself somehow implements it.)
The above example could perhaps contain gMenuSetAttribute(menu,M_CTRL+VK_F4,"ACTIVE",bThereIsAnOpenFile)
CHECKED Set or retrieve the state of a specified checked menu item.
Unlike gRadioItem(), there is no "which one is selected?" query for a radio group on a menu, you'll either have to remember what events your handler was sent, or iterate through all of the menu items until you find it - typically using a manually constructed set of ids and the CHECKED attribute, or perhaps, much more fiddly, via DATA. Also, attempting to unset any member of a radio group quietly does nothing, since the internal handling of clicking on an already set item is significantly simpler that way, plus you don't want to risk it getting left in a nothing selected/invalid state anyway.
You can also use VALUE as an alias of CHECKED, and get exactly the same results.
There is also a CHECKED attribute on a gTree, in case you were looking for that.
DATA[+] (rarely used/needed) Equivalent to (part of) the children parameter, but always in the internal form.
In this one case id is an internal index to said internal form, see next, rather than a keystroke-like id.
There is also a DATA attribute on a gTable and gTree, and DATA handlers on a gList and gGraph.
MDXHIT (read only, rarely used/needed) Returns integer {mdx,hit} for the specified potentially keystroke-like id (crashing should such not exist) such that as noted above mdx is suitable for retrieving DATA, then hit subscripting the MX_ITEMS of that.
IMAGE Set/replace a gImage for the menu item, typically 16x16 but up to 30x22 (auto-centred).
Ignored/overidden on checked/radio items, which use their own 13x13 images. Default: NULL.
It seems generally unwise to put images on submenus, but theGUI makes no attempt to hinder that.
There is also an IMAGE attribute on a gButton and gTree, in case you were looking for them.
TITLE Use a '&' to indicate a mnemonic, and "&&" for a literal ampersand. UTF-8 should be fully supported.
Handlers: Usually specified at creation time, or may be set using eg gSetHandler(menu,"HANDLER",handler).
HANDLER A routine that deals with/implements all menu interactions.

function/procedure handler(gdx menu, integer id [, bool bHover])
menu: identifier of the (toplevel) menu, as originally returned from gMenu().
id: identifier of the menu entry (must be unique within the given menu).
bHover: (optional) 
when false the event is an actual click or keyboard activation,
when true the selection/hover has changed (to id, which may be 0).

When there is no bHover parameter only activation events are forwarded. Some applications may benefit from displaying a longer description of what a menu entry does in a status bar, say, as mouseover and similar events occur. Likewise some menu checks may have no immediate effect so there is nothing to be done straightaway. As noted above, signals from sub-menus opening (there are no close signals) and highlighting events are only sent when an id is actually specified on them (and it is illegal not to have a valid id on a leaf node, which covers check events in that regard).

A menu handler can also invoke gGetOpenFileName().

When bHover is false, a return of TG_CLOSE from a radio or checked item closes the menu rather than anything else, on other items on a menu attached to a dialog closes that dialog, but is simply ignored from a popup menu handler. The handler may as well be a procedure should no dialog need closing, and there are no should-close toggles, aka it never returns or wants to return TG_CLOSE anyway.
Technicalia The nested form above, which I'll reproduce (reindented) here for clarity: 

{{"&File",
  {{"&New\t",M_CTRL+'N'},
   {"&Open\t",M_CTRL+'O'},
   {"&Recent Files",{}}, 
   {"&Close\t",M_CTRL+VK_F4},
   '|',
   {"E&xit\t",M_ALT+VK_F4}}}, 
 {"&Edit",M_NOT_KEY+'E',
  {{"Copy",M_CTRL+'C'}}},
 {"&Help",VK_F1}}

is automatically converted into the equivalent internal form: 

{{{{"&File",2,0,1,0},
   {"&Edit",4,0,1,M_NOT_KEY+'E'},
   {"&Help",0,0,1,VK_F1}},0,0,1,0},
 {{{"&New\t",0,0,1,M_CTRL+'N'},
   {"&Open\t",0,0,1,M_CTRL+'O'},
   {"&Recent Files",3,0,0,0},
   {"&Close\t",0,0,1,M_CTRL+VK_F4},
   {"-",0,0,0,0},
   {"E&xit\t",0,0,1,M_ALT+VK_F4}},1,0,1,0}, 
 {{},2,0,1,0},
 {{{"Copy",0,0,1,M_CTRL+'C'}},1,0,1,0}

While not actually very difficult to follow, it is of course somewhat more tedious and error prone to specify it that way.
The internal form here has four menus: main, file, recent, and edit respectively, each {items,parent,image,enabled,id}.
Each element of the items sequences is {text,submenu,image,enabled,id[,chk]}, with a text of "-" (nb not "|", '-', or '|') making it a separator, a submenu of 0 making it a leaf item, image a negative gdm or NULL or "?"/"??" for checked/radio items with chk present and otherwise that absent, and id being the potentially keystroke-like thing mentioned above.
The DATA attribute allows access to each (whole) menu one at a time, with "DATA" getting you a copy and "DATA+" a temporarily nulled sole owner entry which can be modified without deep_copy() and you are expected to replace asap.
Also, "DATA*" which is intended solely for hMenu.exw, gets a read-only copy of the runtime extras stuff - formally undocumented, but a quick search for CX_MEXTRA in hGUI.e should tell you everything you need to know.
In gMenu.exw new/open add an entry to the recent files menu and close removes one, kept as simple as possible.
While invoking gMenu() sets the whole thing, there is no way to do that later, or alter how many menus there are.
Likewise modifying parent/submenu links is a whole ball of mud I'm not going anywhere near or saying anything useful about, except to suppose you could define a full set and swap them in/out depending on whatever was clicked on.
Attempting to update menus while they are actually on-screen may or may not lead to undefined behaviour.
There may very well be cases where building the internal form is in fact easier than constructing a nested form, however certain niceties such as checking for duplicate ids or auto-checking the first item in a radio group only occur when converting the nested to internal form, and not when you provide the latter. .

The point being made here is that menus are designed to be dirt-simple to define and use in the way mother nature intended, but there is significant complexity hidden behind the scenes, that any clever/fancy/custom stuff inevitably exposes, and equally if prepared to roll up your sleeves and get your hands (very) dirty there is nothing to stop you.

Obviously gPopupMenu() always displays the first entry in the structure/table, before any of its submenus.
Likewise said appears as a barmenu when incorporated into a dialog, but there is no difference in their specification.
You can in theory (aka not fully/formally tested) use gGetAttribute(menu,`VISIBLE`) to determine whether a popup is (still) on-screen, however that will always return true for a menubar, unless you have deliberately hidden it - which, incidentally, is the (main) reason why a barmenu cannot be reused as a popup, although theGUI itself uses much more convoluted and lower level methods which also determine the lowest-level submenu visible.

Shorthand interpretation

The most important rule (in the nested form) is whether item[$] is integer (leaf) or sequence (submenu).
With that, when menu entries are defined as length 5 there can be no misinterpretation of their meaning.
The following (hopefully intuitive) shorter definitions of menu entries are all valid and interpreted as shown: 

                {"leaf", id}                                -- (nb: id>0)
                {"leaf", enabled, id}                       -- (enabled>=0)
                {"leaf", image, id}                         -- (image<0)
                {"leaf", image, enabled, id}                -- (  ""   )
                {"leaf", image, enabled, ignored, id}       -- (chk ignored)
                {"leaf", "?[?]", checked, id}
                {"leaf", "?[?]", enabled, checked, id}      -- (unambiguous)
                {"submenu", children}
                {"submenu", id, children}                   -- (id>0)
                {"submenu", enabled, id, children}          -- (enabled>=0)
                {"submenu", image, children}                -- (image<0)
                {"submenu", image, id, children}            -- (image<0)
                {"submenu", image, enabled, id, children}   -- (unambiguous)

For instance, {"submenu",image,children} is distinguished from {"submenu",id,children} by images being <0.
As stated above, checked and radio items use their own images (if you wanted to override them, maybe one day but not yet, that would obviously be at the system level rather than the menu line level anyway, or maybe, again one day, {on,off}} would be ok for checked items but not radios), with checked only meaningful after "?"|"??".
[Technically/pedantically speaking the formal specification given above slightly misses the point on enabled/checked, that much I already know.]
Incidentally, an id of 0 is only valid in the very last case, and similar to the handling of paranormalised functions additional checks are performed post-reshuffling, specifically image<=0 or (leaf only) "?[?]", enabled,checked in [0,1], id>0 on leaf entries or >=0 on submenus, plus a few extra-paranoid sanity checks such as integer(id) and not string(children).

The standard practice of popping up/left of the cursor occurs when using TG_MOUSPOS and clicking too near the right hand or bottom edge of the screen, and thankfully, since I re-implemented menus from scratch, the horror of tiny almost unusable menus with silly scrollbars on GTK2 all goes away (not that anyone should still be using that).

Minor point: gdk_screen_get_monitor_workarea() is not available in GTK2, so gdk_screen_get_monitor_geometry() used instead, which means some menus may overlap the taskbar slightly. I could easily make GTK3 use the better one.

Note that should you initiate custom drag, it becomes your responsibility to hide any menus, which of course you can safely ignore if you don't know what custom drag is, and to be fair, I haven't added any way to do that in theGUI, yet.
