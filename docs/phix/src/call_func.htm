call_func / proc

Definition: object x = call_func(integer rid, sequence args)
-- or --
call_proc(integer rid, sequence args)
Description: Dynamically invoke a user-defined function/procedure.

rid: a valid result from routine_id(), or (better yet) a plain routine identifier.
args: a sequence of arguments compatible with rid, both type-wise and with length(args) in minp..maxp.
pwa/p2js: Supported.
Comments: When the compiler knows precisely which routine is being invoked it is known as a static call, conversely this is known as a dynamic call, whereby some additional checks (and sequence-unpacking) occur at run-time.
The ability to store tables of these things is often incredibly useful and flexible, especially for gui programming.
When (and only when) the compiler knows that some variable r is an integer, the more familiar-looking syntax r(a,..z) is in fact just shorthand for call_func/proc(r,{a,..z}), and of course when it knows that r has a specific value it reverts to emitting the more efficient static call code.
Note that some programming languages have an explicit "unpack args" syntax such as r(s...), but there is no equivalent in Phix and you must invoke these routines explicitly instead.
A run-time error occurs if you pass a function to call_proc(), or a procedure to call_func().

If the routine has no parameters then args should/must be {}.

Warning: call_func/proc() are known to pepperblast your data with refcount leakage (see below).
That means you will occcasionally need a few deep_copy() that logically you should not, but at least said leaks are automatically repaired by subsequent calls and when the offending invisible temporary variables are reused, rather than being the kind that causes your program to slowly run out of memory. Refactoring call_func/call_proc code into independent subroutines can often eliminate such issues entirely, as said temps get cleaned up on exit.
Plus of course when the contents of args is effectively read-only, you simply don't care about any of this.
Example: 
function sum2(integer a, inteber b)
    return a+b
end function
integer r_sum2 = sum2 -- [same as routine_id("sum2")]

?sum2(1,2)                  -- direct/static call
?call_func(r_sum2,{1,2})    -- indirect/dynamic call
?r_sum2(1,2)                -- <compiler decides>
Implementation: via :%opCallFunc and %opCallProc in builtins\VM\pcallfunc.e (an autoinclude) - low-level complicated stuff!
While it works fine, the frankly hideous and grotesquely inefficient existing code thoroughly deserves to be scrapped and replaced with something much better. [Using %opCallFunc and %opCallProc in an attempt to speed them up was probably a retrograde step: hll shims to that sort of low level code might in fact significantly reduce refcount leakage - similar to, say, allocate(), which indeed turned out noticably better than using %pAlloc directly/everywhere.]
Some additional notes on first class routine_ids can be found in the technicalia drop-down of routine_id.
In a way, p2js.js cheats, since JavaScript can pass actual functions around and invoke them just as easily as Phix can do with these integers.
